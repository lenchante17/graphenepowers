# Brainstorming Facilitation

Use these interaction rules while running the design conversation.

## Conversation Rules

- ask one question per message
- prefer multiple choice when practical
- keep alternatives open until the user approves the concept
- ask only questions that reduce design ambiguity, scope ambiguity, or contract ambiguity
- if the request describes multiple subsystems, decompose before drilling into details
- use the Stage 2 guide to teach the user the relevant design space before pushing them to choose
- keep Stage 2 research and Stage 3 option generation with the same main agent so the option set reflects the gathered context
- use the Stage 3 concept brief to batch option selection when the user can reasonably answer several design choices at once
- move from Stage 2 into Stage 3 without an artificial stop when the guide already gives enough context to frame the concept options

## Presentation Rules

- present concept and high-level structure before low-level detail
- when comparing directions, lead with the recommended option and explain the tradeoff
- validate major sections incrementally instead of dumping the entire design at once
- in `contract-confirmation`, present the contract summary and unresolved risks rather than forcing a full alternatives discussion
- make option documents scannable: recommended option first, tradeoffs explicit, user choices easy to reply to in one pass
- treat the concept brief response as the explicit go or no-go signal for writing the detailed spec

## Visual Companion Rule

- offer the visual companion in its own message only when upcoming choices are genuinely visual
- if the user accepts, keep using the terminal for text-only decisions
- read `visual/visual-companion.md` before using the browser flow
